THE ENGINE · WHAT VESPA IS

Not a vector database — a ranking engine

Most RAG stacks are a vector index plus application code. Vespa is a search engine where a document holds tensors, and ranking is an expression the engine evaluates next to the data. The difference shows up the moment one document needs more than one vector.

vector index + app code (e.g. pgvector)
vespa
vectors per document
One vector per column. A 40-chunk document becomes 40 rows, regrouped in application code.
tensor<int8>(chunk{}, x[96]) — every chunk vector lives inside the document, and rank expressions reduce over them.
lexical + semantic
Vector index only. BM25 comes from Postgres full-text search or a separate extension; the two are fused in app code.
BM25 and ANN in one query, fused in the rank profile — userInput() or nearestNeighbor().
reranking
Candidates cross the network first; the application reranks what it got back.
Phased ranking in-engine — cheap scoring over everything, then an expensive model over only the survivors.
model inference
None. Embeddings are produced outside the database and inserted.
ONNX models run in the engine: embedder, cross-encoder, ColBERT, LightGBM. This study ran three at once on an 8 GB laptop.
filtering
With approximate indexes the filter is applied after the index scan; iterative scans exist to claw the recall back.
Attributes filter during matching, so a tenant filter is a matching constraint rather than a ranking preference.
why it matters here
Late interaction, per-chunk scoring and top-k chunk selection are not features you wait for — they are rank expressions you write. Every technique in this deck is a change to a text file, not a new service.
pgvector as the reference point  ·  it is the common default, and the comparison is about what one engine does in one query — not product quality

THE STARTING POINT

The Vespa RAG Blueprint

Vespa's reference application for RAG — a complete, opinionated stack meant to be deployed as-is. Everything below is a default: what you get before writing a line of your own.

01schema & chunking
  • Documents are chunked in the schema — fixed-length 1024
  • Produces a BM25-indexed chunks array and a per-chunk embedding tensor
  • No external chunking service, no second store to keep in sync
02embeddings
  • A ModernBERT embedder runs in-engine, at index and query time
  • Packed to 1 bit per dimension (int8, hamming distance)
  • A float query vector is kept for cosine rescoring
03retrieval
  • One query, three retrievers: lexical or ANN on the title vector or ANN on the chunk vectors
  • targetHits:100 per neighbour search
  • Shipped as query profiles — hybrid · rag · deepresearch
04ranking
  • First phase: a learned linear model over 7 features
  • Its weights ship as constants in the query profile
  • Second phase: an optional LightGBM GBDT over richer features
05chunk selection
  • top(3, chunk_sim_scores) — a tensor expression, not app code
  • Picks which paragraphs reach the LLM, not just which documents
  • Delivered by the summary via select-elements-by
06generation
  • The rag profile chains an LLM client onto the same query
  • Tokens stream back over SSE
  • Retrieval and generation are one deployment
not included
No tenant concept, no cross-encoder, no late interaction — those are this study's additions.

retrieval is the whole game
THE PROBLEM

RAG — retrieval is the whole game

What it is
Retrieval-Augmented Generation: find the relevant passages, then let an LLM write the answer from them.
How it works
Two stages — a retriever pulls the top-k passages; a generator conditions on them. The generator can only be as right as what it's handed.
The tradeoff
All the leverage is upstream. A perfect generator over bad retrieval still answers wrong; a modest generator over good retrieval is fine.
What we saw
The generator was flawless — faithfulness 1.00, zero hallucination, declined 8/8 unanswerables — yet correctness (~0.50) was capped entirely by retrieval recall. The study's core premise, confirmed: get retrieval wrong and every answer downstream is wrong too.

vespa-rag-blueprint-stress-test  //  ways to match
lexical vs semantic
WAYS TO MATCH

Two ways to match: lexical vs semantic

What it is
The core dichotomy. Lexical matches words; semantic matches meaning.
How it works
BM25 scores by term overlap weighted by rarity — rare shared words count more. Dense embeds query and doc into vectors; similarity is cosine.
The tradeoff
BM25 nails exact terms, acronyms and rare tokens but dies on vocabulary mismatch. Semantic bridges wording but blurs fine distinctions and collapses when many docs are near-identical.
What we saw
Query style flipped the winner. Verbatim questionnaire re-runs: BM25 0.957, semantic 0.915. Reworded questions: BM25 collapses to 0.279, semantic wins. Neither alone is enough.

hybrid fusion
WAYS TO MATCH

Hybrid retrieval & fusion (RRF)

What it is
Combine lexical + semantic so each covers the other's blind spot.
How it works
Run both, then merge. Reciprocal Rank Fusion adds 1/(k+rank) from each list — rank-based, so it needs no score calibration and no training.
The tradeoff
Robust and free — no tuning — but untuned. A trained combiner can beat it if you have labels, and it can't fix a signal that's simply absent.
What we saw
On reworded questions, untrained RRF (0.489) beat the blueprint's trained linear ranker (0.436). Structure beat a learned model — a recurring theme.

how you cut documents
REPRESENTATION

Chunking: how you cut documents

What it is
Documents are split into passages before embedding and indexing.
How it works
Fixed-size (e.g. every 1024 chars) is simple; semantic / paragraph-aware splits on natural boundaries.
The tradeoff
Big chunks keep context but blur what they're "about" — a chunk about five things matches everything (a cosine attractor). Small chunks are precise but can sever an answer mid-thought.
What we saw
Fixed-1024 split a password policy mid-sentence and let a generic intro chunk win context slots. Paragraph chunking fixed both — invisible to doc-level metrics, decisive at the chunk level. You only see it if you judge chunks, not docs.

vespa-rag-blueprint-stress-test  //  ways to rank
the compute funnel
WAYS TO RANK

Phased ranking: the compute funnel

What it is
Rank in stages, cheap-to-expensive, each stage re-ranking fewer docs.
How it works
first-phase (cheap, all candidates) → second-phase (costlier, top-N) → global-phase (most expensive, top-few). Vespa names these literally.
The tradeoff
Lets you afford an expensive model by running it only on a shortlist — but the shortlist is only as good as the cheap stage's recall. A weak first phase forces a wide, expensive rerank window.
What we saw
Recall@10 runs 0.43–0.69 on paraphrases — on a third or more of queries the gold answer never reaches the top-10 at all, and no reranker can save what was never retrieved. First-phase recall is a real constraint here.

vespa-rag-blueprint-stress-test  //  ways to rank
pointwise vs pairwise
WAYS TO RANK

Learning to rank: the objective matters

What it is
Train a model to order results, over cheap features (BM25, similarities…).
How it works
Pointwise predicts each doc's relevance score independently. Pairwise learns which of two docs should rank higher (RankNet-style). Listwise optimizes the whole ordering.
The tradeoff
Pointwise is simple but optimizes the wrong thing — absolute scores, not order — so it can rank worse than its own best feature. Pairwise matches the task (ordering) and needs graded pairs.
What we saw
On the small corpus, pointwise lost (0.902 vs zero-shot 0.950) and pairwise won (0.956). In distillation it reversed — pointwise 0.604, pairwise 0.553. That comparison confounds objective with model class, so the objective matters less than "confirmed 3×" implied.

vespa-rag-blueprint-stress-test  //  ways to rank
the accurate, expensive reranker
WAYS TO RANK

Cross-encoders: accurate, expensive

What it is
A transformer that reads query and document together and outputs a relevance score.
How it works
Concatenate [query, doc], run one full transformer pass, read the score. Joint attention sees exact interactions a vector dot-product can't.
The tradeoff
The most accurate reranker available — but you pay a full model forward pass per (query, doc) pair, at query time. Latency scales with how many you rerank.
What we saw
Lifted the hard case 0.505 → 0.576 at ~2.5 s/query on CPU — a real gain, but beaten outright by the library model (0.635), which costs nothing. The "expensive cross-encoder" stage: justified, but costly.

vespa-rag-blueprint-stress-test  //  late interaction
ways to rank
WAYS TO RANK

Late interaction (ColBERT): the sweet spot

What it is
Keep a separate embedding for every token in a document, and match at the token level — not one vector per doc, but a whole matrix. ColBERT is the model that popularised this; the name now stands for the technique too.
How it works
MaxSim — for each query token, take its best-matching doc token, then sum. The doc token vectors are precomputed at index time, so query time is a cheap tensor op — no transformer pass per document.
The tradeoff
Near cross-encoder quality at bi-encoder speed — but it stores many vectors per doc (a token matrix), so the index is larger and feeds are heavier.
What we saw
0.517 nDCG@10 at ~60 ms/query — between fusion and the cross-encoder for 1/40th the cost. The cost simply moved to indexing (a third model, slower feeds). Often the right answer to "the reranker is too expensive."

vespa-rag-blueprint-stress-test  //  knowledge distillation
ways to rank
WAYS TO RANK

Distillation: pay once, serve cheap

What it is
Train a cheap student to imitate an expensive teacher — capture the big model's judgment in a small, fast one.
How it works
Run the teacher (a cross-encoder) offline to label (query, doc) pairs; train a fast student — a linear/GBDT over features, or a small bi-encoder — to reproduce its ranking. The teacher never runs at query time.
The tradeoff
Most of the teacher's quality at a fraction of the serving cost — but the student is capped by its features, and (again) the training objective matters.
What we saw
The distilled student beat its teacher — 0.604 vs 0.561 — at microsecond cost, and the deployed linear variant serves in ~8 ms vs ~2500 ms (~300× less ranking compute). The expensive reranker becomes an offline teacher, not a serving component.

vespa-rag-blueprint-stress-test  //  representation learning
representation
REPRESENTATION

Bi-encoders & contrastive fine-tuning

What it is
The embedding model itself — and the act of teaching it your domain rather than taking it off the shelf.
How it works
A bi-encoder embeds query and doc separately (fast, cacheable). Contrastive fine-tuning pulls matching pairs together and pushes mismatches apart; MultipleNegativesRankingLoss uses the other items in the batch as free negatives.
The tradeoff
Fine-tuning attacks the retrieval ceiling directly — the highest-leverage representation lever — but it needs domain pairs (real or synthesized) and compute, and over-fitting on little data is a real risk.
What we saw
Fine-tuning a small MiniLM on 195 generated paraphrase pairs lifted it 0.591 → 0.622 (+0.031) — the only trained component to beat its zero-shot baseline (the rankers all tied). Fixing the representation matched the actual failure mode: vocabulary mismatch.

vespa-rag-blueprint-stress-test  //  quantization / binarization
representation
REPRESENTATION

Quantization: the memory–quality dial

What it is
Shrink embeddings by storing them at lower precision — trade a little accuracy for a lot of memory and speed.
How it works
float32 → int8, or all the way to 1-bit binary; compare with cheap distances (hamming for binary). Optionally rescore the top-k in full precision to claw quality back.
The tradeoff
Massive storage and latency savings for a small, measurable quality loss — and you can buy most of that quality back by rescoring finalists in float.
What we saw
Binary cost ~0.053 nDCG (~12%) for 32× smaller vectors on the hard case. The right default at scale (thousands of docs × dozens of tenants); recover the gap with binary recall + float rescoring of the top-k.

vespa-rag-blueprint-stress-test  //  the library model
rfp-specific
RFP-SPECIFIC

The library model: match the question

What it is
Retrieve against past questions, not past answers — the RFP-specific insight that reframes the whole problem.
How it works
Index your curated Q&A library keyed on the stored question text; embed the incoming (reworded) question, match it to the closest stored question, then return its vetted answer.
The tradeoff
Hugely effective when questions recur (security questionnaires) — but it depends on having a curated library and on that recurrence; bespoke, one-off questions benefit less.
What we saw
Matching question→question lifted single-vector semantic 0.505 → 0.635, same embedder — only the indexed field changed. The best arm in the whole study, and free. This is why real RFP tools are built around answer libraries, not raw-document RAG.

vespa-rag-blueprint-stress-test  //  hyde — rewrite the query
query-side
QUERY-SIDE

HyDE: rewrite the query, not the ranking

What it is
Have an LLM write the hypothetical document a query should match, and embed that instead — the canonical query-side intervention, and the one stage this study hadn't tested.
How it works
Two directions: classic HyDE writes a hypothetical answer (into answer space); the symmetric variant reconstructs the standard question being paraphrased (into question space — where the library model says the signal is). Concatenating the original query hedges wrong reconstructions.
The tradeoff
A ~2 s LLM call per query — cross-encoder-class latency, cacheable across repeat questions. Aimed at the wrong target space, the call is wasted; aimed right, it competes with the best arm in the study.
What we saw
Direction decided everything. Answer-space never touched the library model (−0.129, p<0.0001). Question-space + original query hit 0.719 on 47 queries — best number yet — then failed out-of-sample confirmation at 232 (+0.023, p≈0.24). Confirmed instead: it beats the equal-cost cross-encoder (p≈0.001), and rewriting without the original query is actively harmful (−0.073, p≈0.003).

vespa-rag-blueprint-stress-test  //  structural wins
rfp-specific
RFP-SPECIFIC

The "boring" structural wins

What it is
The unglamorous mechanisms that mattered most — tenancy, freshness, dedup. Plumbing, not models.
How it works
Tenant isolation = a hard metadata filter (never let ranking decide it). Freshness = prefer the newer of near-duplicates (a tie-break), not a global ranking feature. Dedup = collapse near-identical answers.
The tradeoff
Cheap, robust, and often the biggest wins — but because they're plumbing they get overlooked. A global "freshness feature" actively misleads; freshness only discriminates between duplicates on the same topic.
What we saw
The hard tenant filter was the single biggest relevance intervention (+0.035, p<0.001) and, on the questionnaire corpus, was worth +0.15 to +0.29 while removing ~350 cross-tenant leaks per arm. A global freshness weight learned negative; dedup-then-prefer-fresh worked (+0.011). Structure beat learned ranking repeatedly.

vespa-rag-blueprint-stress-test  //  the generation stage & the limits
the closer
THE GENERATION STAGE

Drafting the answer — and its limits

What it is
Drafting the answer, and knowing what this study does — and does not — prove.
How it works
Prompt the LLM with retrieved context and instruct it to answer only from that context, declining if it's not covered. Faithfulness and abstention are the safety properties for a compliance product.
The tradeoff
A well-instructed generator turns retrieval misses into an honest "not covered" instead of confident wrong answers — but that holds for atomic-answer domains; synthesis and essay questions make the generator do real, harder work.
What we saw
Perfect faithfulness and abstention — the generator answered only from context and declined every unanswerable. Correctness (~0.50) was capped entirely by retrieval, exactly as the two-stage model predicts.
the honest limit
Our data is security-compliance — a standardized best case — and the corpus is LLM-generated. The architecture (filter, library model, phased ranking, distillation, fine-tuning) should port; the magnitudes (BM25's dominance, the library jump) won't. Pricing, capabilities, and essay questions are untested. Know the limits of your eval.

vespa-rag-blueprint-stress-test  //  evaluation & statistical rigour
how you know
HOW YOU KNOW IT WORKS

How you know it works

What it is
Measuring retrieval honestly — the part that is easy to fool yourself on.
How it works
nDCG@10 (graded, position-weighted) over TREC qrels; grouped cross-validation (never test on a query you trained on); paired bootstrap (is a delta real or noise?); chunk-level judgments; leakage accounting.
The tradeoff
Rigorous eval is slow and unglamorous — but without it you ship noise. In-sample numbers flatter; small samples lie.
What we saw
An in-sample fit looked like a +5-point win that grouped CV revealed as a loss; a "pairwise beats zero-shot" result evaporated (p≈0.98) when we scaled the query set. The measurement rig caught — and killed — findings the metrics alone would have shipped.

THE FINDINGS

The through-lines

01
Structure beats learned ranking at this scale.
Every durable win was structural — hard tenant filter (+0.035, p<0.001), paragraph chunking, dedup-freshness, the library model. Learned rankers repeatedly tied zero-shot.
02
The ranking objective matters — but less than we claimed.
Pointwise lost to pairwise in Experiments 2 and 4 — then reversed in distillation (0.604 vs 0.553). That comparison confounds objective with model class, so the "confirmed 3×" version was overstated. Retracted here rather than quietly dropped.
03
The expensive cross-encoder makes things worse.
Stacked on the library model it scores 0.578 vs 0.635 without it — rescoring near-identical answers reintroduces the confusion matching questions removes. As an offline teacher it distils to a student that beats it (0.604 vs 0.561) at ~8ms.
04
Corpus difficulty is a dial — and you set it.
The 39-doc set was near-ceiling for most retrievers, so a harder one was built: 940 near-identical answers to one shared question set. Calibrating it took three attempts — too duplicated, then too easy, then right. Every number here is conditional on that choice.
05
The measurement infrastructure was the real product.
Leakage accounting, grouped CV, paired bootstrap, and chunk-level qrels are what found — and killed — findings that noisy metrics would have shipped. Its latest kill: the HyDE rewrite's 0.719 headline, retracted by scaling the query set 47→232 (+0.023 out-of-sample, p≈0.24).

FINAL THOUGHTS

What we proved, and what's left

validated — in depth
The search-quality half of the architecture: retrieval, ranking, chunking, distillation, query-side rewriting (HyDE), and the measurement rig that keeps them honest.
needs the cluster
The production-systems half — cluster sizing, multi-region reliability, observability, hosted model serving — needs real production infrastructure, not a laptop.
honest limitations
The corpus is generated. One model wrote all 940 answers, so the register is more uniform than real filed text. This is the study's biggest caveat — the highest-value hardening is a real, licensable RFP corpus plus independent expert judgments.
Narrow test domain. The corpus is security compliance — a standardized, best-case slice of an RFP. The architectural wins should port; the magnitudes (BM25's swing from 0.957 verbatim to 0.279 on paraphrases, the library-model jump) won't. Pricing, capabilities and free-text essay questions are untested.
This study set out to diagnose before optimising, and not to fool itself with noisy results. That discipline is exactly what it kept having to apply to its own findings.

reference
GLOSSARY · I

The vocabulary — retrieval & ranking

Embedding
text turned into a vector of numbers; nearby vectors mean similar things.
Sparse vs dense
sparse = word-count vectors (BM25); dense = learned meaning vectors.
ANN / HNSW
approximate nearest-neighbour search — finds close vectors fast via a graph index instead of scanning every doc.
Cosine / dot / hamming
ways to measure vector closeness: angle between vectors / raw overlap / differing bits (for binary).
Tokenization
splitting text into the sub-word units a model actually reads.
Reranking
a second, pricier pass that reorders an already-retrieved shortlist.
Recall vs precision
recall = did we fetch the right doc at all; precision = how much of what we fetched is right.
Rank profile / phases
Vespa's scoring config; first / second / global-phase = cheap→expensive ranking stages.
top-k / targetHits
how many candidates a stage keeps and passes to the next.
Match-features
feature values Vespa exposes per hit — the raw material for training a ranker.
Index-time vs query-time
work precomputed when docs are ingested vs work done per search (latency lives here).
Chunk / passage
the slice of a document that actually gets embedded and retrieved.

reference
GLOSSARY · II

The vocabulary — models, training & eval

Cross- vs bi-encoder
reads query+doc together (accurate, slow) vs separately (fast, cacheable).
Late interaction (ColBERT)
per-token vectors compared with MaxSim — near cross-encoder quality, precomputed.
GBDT / LightGBM
gradient-boosted decision trees; a fast non-linear ranker over features.
Pointwise / pairwise
predict each doc's score alone vs learn which of two ranks higher (RankNet).
Contrastive fine-tuning
pull matching pairs together, push mismatches apart, to teach an embedder your domain.
In-batch negatives
during training, the other items in the batch serve as free “wrong” examples.
Zero-shot
using a model as-is, with no task-specific training.
Distillation
train a cheap student to imitate an expensive teacher's scores; serve the student.
Quantization
store vectors at lower precision (int8 / 1-bit) to save memory, with optional float rescoring.
ONNX
a portable model format Vespa runs in-engine for embedding and reranking.
nDCG / MRR
quality metrics: graded, position-weighted score / one-over-rank-of-first-correct-hit.
qrels · CV · bootstrap

GLOSSARY · III

The vocabulary — names, generation & stats

ColBERT
the late-interaction model itself — a BERT that emits one vector per token; the name gets used for both the model and the method.
BM25
the standard lexical score: shared terms, weighted by rarity, damped for repetition and document length.
RRF (reciprocal rank fusion)
merge two ranked lists by adding 1/(k+rank) from each — rank-based, so no score calibration and no training.
HyDE
LLM-write the hypothetical document a query should match and embed that; which space you rewrite into (answer vs question) decides whether it helps.
Grounding
answering only from the retrieved context, never from what the model already knows.
Faithfulness
does the answer actually follow from the context it was handed — scored separately from whether it is correct.
Hallucination
confident output the retrieved context does not support.
Abstention
declining when the context doesn't cover the question — the safe failure mode for compliance.
p-value
odds of a gain this big if the change did nothing. Small = real (p<0.001); large = noise (p≈0.98).
Leakage
test information reaching training — e.g. tuning on queries you then score on. Inflates every number.
In-sample vs held-out
scored on the data you fitted on vs data the model has never seen. In-sample always flatters.
Over-fitting
learning the training set's noise — looks excellent in-sample, fails on new queries.
Loss function
what training actually optimizes; pick one that doesn't match the task and a better model ranks worse.
